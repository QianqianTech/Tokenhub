# 运营仪表盘时间范围与状态优先设计

## 目标

将 `#/operations/dashboard` 调整为面向日常运营的工作台：用户先选择统计时间阶段，再在首屏识别调用、异常、延迟和安全风险，随后按需查看趋势、排行、性能、安全和多模态归因。

## 范围与约束

- 只修改管理员仪表盘的前端渲染、样式和前端契约测试。
- 继续使用现有六个 `/admin-api/dashboard/*` 查询接口；不修改 Docker、Caddy、环境变量或数据库结构。
- 所有查询已支持 `from` 与 `to`，前端必须把同一时间区间传给全部六个接口。
- 保留趋势粒度、排行维度、排行排序及既有下钻导航。

## 交互与页面结构

顶部筛选栏新增时间阶段：`今日`、`近 7 天`、`近 30 天`、`自定义区间`。常用阶段自动计算 UTC 起止时间；自定义区间显示起止日期时间输入，并在开始时间晚于结束时间时阻止刷新并给出中文提示。

筛选结果按以下顺序渲染：

1. 当前区间摘要：请求数、成功率、异常请求、总 Token、平均延迟和成本。
2. 运营状态条：显示当前选择的时间段、异常请求数、最新 P99 延迟和安全事件数；有异常时使用文字化的“需关注”提示，正常时显示“运行平稳”。
3. 趋势图、排行、多模态、安全、性能分析。所有区块保持既有下钻能力和空态。

## 数据流与错误处理

`dashboard.js` 根据时间阶段生成 `{ from, to }`，与现有 `{ bucket, dimension, sort }` 合并为一份 `params`，供六个并发 API 请求共用。服务端仍负责权限范围与聚合表查询。筛选控件的时间范围变化不自动请求，只有用户点击“刷新”或提交表单才刷新，避免连续输入自定义时间时产生无效请求。

## 验收

1. 前端源码契约测试证明有时间阶段控件、开始/结束时间控件、统一的 `from`/`to` 参数以及无效区间提示。
2. 前端源码契约测试证明首屏含区间摘要和运营状态条，并保留趋势、排行、多模态、安全和性能图表。
3. 聚焦前端测试通过；在可登录的本地管理后台以“近 7 天”和自定义区间各验证一次。

## 非目标

- 不增加新的数据接口、告警规则或阈值配置。
- 不改变大屏分享页面、权限模型或服务端聚合逻辑。

# API Key 模型授权编辑修复设计

**状态：** 推荐方案已获确认，等待书面设计复核

## 背景

Admin 的 API Key 表单包含“允许模型”，但现有读取和写入链路没有闭合：API Key 列表不返回真实的 `model_ids`，编辑弹窗因此不能回显已保存的模型授权；编辑保存又调用普通 `PUT /admin-api/api-keys/{id}`，而 `ApiKeyService::update()` 会忽略 `model_ids`。真正替换模型授权的 `PUT /admin-api/api-keys/{id}/models` 存在，但当前编辑弹窗没有调用。

结果是管理员可以在界面中看到或选择多个模型并收到“保存成功”，数据库中的 `api_key_model_permissions` 却保持不变。`GET /v1/models` 以该授权表为真值，因此终端只返回数据库中真实绑定的模型。

## 目标

- 让 Admin API Key 页面准确回显每个 Key 的真实模型授权。
- 让一次编辑保存原子地更新 Key 基础信息和模型授权。
- 允许 `model_ids: []`，其含义是该 Key 不能调用任何模型。
- 对非法、未知或不允许写入的模型 ID 在修改数据前返回明确错误。
- 保存成功后立即清理该 Key 的认证缓存，使 `/v1/models` 反映最新授权。
- 保留已有专用模型替换接口，并让两个写入入口复用同一套验证与持久化逻辑。
- 防止管理员修改其部门管理范围之外的 API Key。

## 非目标

- 不改变模型管理页的全局启用/停用语义。
- 不改变模型限额、限额策略或限额绑定的语义。
- 不改变 `/v1/models` 的返回筛选规则。
- 不新增数据库表或迁移。
- 不自动把所有启用模型授权给新 Key。
- 不修改 `/v1/management/*` 的部门边界和授权模型必须为启用状态的现有规则。

## 核心语义

终端可见模型继续定义为：

```text
API Key 的模型授权
∩ 模型状态为 active
∩ Provider 状态为 active
```

Admin 编辑请求中的 `model_ids` 采用以下语义：

- 字段缺失：只更新基础信息，不改变模型授权。
- 空数组：清空模型授权；Key 仍可用于其被允许的非模型接口。
- 非空数组：替换为给定模型集合。
- `null`、非数组、非正整数、未知模型或停用模型：返回 `422 ADMIN_INVALID_PAYLOAD`，且不得修改基础信息或既有模型授权。

## 后端设计

### 列表读取

`ApiKeyService::listWithUsage()` 在取得当前页 Key 后，使用一次批量查询读取这些 Key 的 `api_key_model_permissions` 和模型名称，避免逐行查询。每个列表项增加：

```json
{
  "model_ids": [810917, 810918],
  "model_names": ["deepseek-v4-flash", "deepseek-v4-pro"],
  "model_count": 2
}
```

授权表中的停用模型仍应出现在读取结果中，并附带可供前端标注的状态；它不会出现在 `/v1/models`。这样管理员可以识别并移除历史授权，而不是让绑定静默消失。

### 写入与事务

`ApiKeyService` 增加一个共享的模型 ID 规范化与验证路径，以及一个只负责在现有事务内替换授权行的内部方法。

普通 `update()` 在请求含有 `model_ids` 时执行以下顺序：

1. 验证 API Key 存在。
2. 验证基础字段和完整 `model_ids`，所有验证发生在任何写操作之前。
3. 开启数据库事务。
4. 更新允许的基础字段。
5. 删除该 Key 的旧授权并插入新的授权集合；空数组只执行删除。
6. 提交事务。
7. 写入包含基础变更和 `model_ids` 的审计记录。
8. 清理该 Key 的认证缓存。
9. 返回更新后的安全 Key 数据和真实 `model_ids`。

专用 `replaceModels()` 接口复用同一验证和授权替换方法，保持现有路由兼容。验证失败时不能先删除旧授权。

### Admin 管理范围

`AdminController` 增加按 API Key 查询 `department_id` 并调用既有 `requireDepartmentScope()` 的检查。普通更新和专用模型替换都必须先通过该检查。找不到 Key 返回 `404 ADMIN_NOT_FOUND`，越权返回 `403 ADMIN_PERMISSION_DENIED`。

外部管理接口继续使用 `AgentManagementApiKeyService` 的同部门约束，不改用 Admin 会话权限逻辑。

## 前端设计

API Key 编辑弹窗继续作为 Admin Web 中配置 Key 模型授权的唯一入口。

- 列表响应中的 `model_ids` 用于初始化真实选中状态。
- “允许模型”标签明确说明多选方式，以及“不选表示不能调用任何模型”。
- 编辑弹窗一次提交基础字段和 `model_ids` 到普通更新接口，不再产生界面成功但授权未保存的状态。
- API Key 详情增加“已授权模型”和“模型数量”。
- 空授权显示明确警告：“未授权模型，该 Key 不能调用模型接口”。
- 已授权但已停用的模型显示“已停用”标记；管理员保存模型变更时必须移除或替换这些停用模型。
- 保存后重新加载列表，以服务端返回为准重新渲染选中状态和授权摘要。

本次不重构整个通用资源表单。保留现有多选控件，只补充清晰说明和服务端真值回显，避免扩大范围。

## 错误处理

- `model_ids` 类型错误：`422 ADMIN_INVALID_PAYLOAD`。
- ID 为零、负数或非整数：`422 ADMIN_INVALID_PAYLOAD`。
- 任一模型不存在或处于停用状态：`422 ADMIN_INVALID_PAYLOAD`，返回通用消息，不提交部分授权。
- API Key 不存在：`404 ADMIN_NOT_FOUND`。
- Key 不在管理员范围内：`403 ADMIN_PERMISSION_DENIED`。
- 数据库写入失败：回滚基础信息和模型授权，返回现有统一错误响应。
- 认证缓存只在事务成功后失效；失败时保持原缓存和原数据库状态一致。

## 测试设计

### 服务层

- 列表结果对每个 Key 返回真实 `model_ids`、`model_names` 和 `model_count`。
- 更新请求包含两个模型时，基础字段和两条授权同时保存。
- 更新请求包含空数组时，授权被清空，Key 本身保持有效。
- 请求不包含 `model_ids` 时，既有授权保持不变。
- 非法、未知或停用模型导致 `422`，既有基础信息和授权均保持不变。
- 成功替换后认证缓存被清理。

### 权限和接口契约

- 管理范围内的管理员可以更新模型授权。
- 管理范围外的管理员得到 `403`，授权不变。
- 专用 `/models` 路由仍可用，并复用相同验证行为。
- `/v1/models` 在授权增加、减少和清空后分别返回对应模型集合。

### 前端契约

- API Key 编辑表单使用列表返回的 `model_ids` 初始化选中项。
- 编辑保存请求包含 `model_ids`。
- 空授权显示明确提示。
- 详情页展示真实模型名称和数量。

### 验证方式

优先运行聚焦 PHP 服务测试和前端源码契约测试，再通过 Docker PHP 运行相关测试与一次真实只读/临时数据验证。最终用临时 Key 验证：创建多模型授权、`GET /v1/models` 返回多模型、编辑为空后返回空模型列表、恢复授权后再次返回预期模型。

## 验收标准

- Admin 页面看到的已授权模型与 `api_key_model_permissions` 一致。
- 在编辑页增加或移除模型后，重新打开仍显示相同选择。
- 同一个完整 Key 调用 `/v1/models` 与 Admin 页面显示一致，差异仅允许来自模型或 Provider 的全局停用状态，并在 Admin 中明确标注。
- 空模型授权合法且有清晰提示。
- 任何验证或权限失败都不会留下部分更新。
- 现有 API Key 创建、批量启停/删除、模型限额和外部管理接口行为不回归。
